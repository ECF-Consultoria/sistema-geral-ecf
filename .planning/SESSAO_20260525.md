## 2. Bugfixes pós-merge

### OOM no sync-faturamento (`c6e6b17`)
**Arquivo:** `app/Services/AdmanService.php` — método `syncMonthRevenue()`

**Antes:**
```php
$performance  = $this->fetchPerformance($custId, $start, $end);
$summarized   = $performance['summarizedData'] ?? [];
$grossBilling = $summarized['grossBilling']['value'] ?? null;
```

**Depois:**
```php
$grossBilling = $this->fetchGrossBilling($custId, $start, $end, cacheMinutes: 0);
```

`fetchPerformance()` carrega a resposta completa da API (todos os itens de campanha) e
estourava os 128 MB do PHP na VPS ao rodar em loop para muitas empresas.
`fetchGrossBilling()` já faz `unset($data); gc_collect_cycles()` depois de extrair o valor.

### Migração retroativa removida (`d5c30c2`)
**Arquivo:** `database/migrations/2026_05_25_100003_seed_setor_comercial_and_retro_migrate.php`

A ETAPA 3 dessa migration criava um registro em `companies` para cada `mlb_empresa` sem
`company_id`. Isso gerou 122 empresas indesejadas na gestão. A etapa foi removida — o
vínculo `company_id` só deve ser criado quando o Comercial cadastra explicitamente.

| `resources/js/Layouts/AppLayout.jsx` | nav: "Cadastro de Empresas" → "Empresas" |

### Comportamento do `update()`
- Aceita `service_type` agora (antes era somente-leitura)
- Se mudar para `polos`/`assessoria` e não existir `mlb_empresa` vinculada: cria automaticamente
- Se mudar para `publicidade`/`gestao`: apenas atualiza o campo (não deleta registros MLB existentes)

### Comportamento do `destroy()`
- Faz `active = false` (não deleta fisicamente)
- Registros relacionados (mlb_empresas, sugadores, etc.) são preservados
