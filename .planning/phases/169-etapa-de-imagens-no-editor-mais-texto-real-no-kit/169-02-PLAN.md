não reabrir `CreativePlanner::montarPrompt()`/`validarTexto()` (a chamada ao LLM) e para não
depender da fidelidade do modelo em ecoar um fato que ele nunca viu; (3) a API do Publicador ganha
os três endpoints que o operador usa para confirmar, listar e remover um fato, e que respondem
"o que falta" quando não há fato suficiente para nenhum slot de texto (TXT-04).

Por que o preenchimento é DETERMINÍSTICO (não pelo LLM): a medição do spike (261001-nkx §17) provou
que texto DADO no prompt sai exato nos três modelos testados — a mesma garantia vale aqui sem
precisar mostrar o fato ao modelo de TEXTO (que decide headline/badge) e sem reabrir a validação
`validarTexto()` que já audita o que sobrevive à reconciliação. Copiar o texto confirmado direto
para `CreativeSlotPlan::$badges` é estritamente mais seguro que confiar no LLM para repeti-lo.

Este plano NÃO toca `Editor.jsx`/`apoio.js`/`EtapaDetalhes.jsx` — os três endpoints são consumidos
pela tela em 169-03, dentro do painel que JÁ existe hoje (sem mexer na estrutura de etapas).
