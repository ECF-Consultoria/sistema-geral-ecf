<o_mecanismo_do_estado_na_url>
## ⚠️ LIST-19 — o mecanismo, medido e decidido

**O que a tela já faz hoje** (`MeusAnuncios.jsx`, `navegar()`):
```
router.get(route('mlb.anuncios.meus', { company: empresa.id }),
           { sub, busca, status, motivo, ...params },
           { preserveState: true, replace: true })
```
➡️ **O estado JÁ vive na URL.** Isto não é mecanismo novo: é **ampliar o que já existe** dos 4
params de hoje para os 12 do plano 180-04. E o servidor já devolve tudo em `filtros`, que a página
lê como fonte da verdade.

**Por que `router.get` com query string, e não `history.pushState`:**
  · a busca e os filtros são **do servidor** (D-05): a paginação é de 50 e filtrar no cliente
    mentiria sobre as outras dezenas de milhares de linhas do acervo;
  · `preserveState: true` mantém o estado efêmero (scroll de popover, `copiada`, `colapsados`) sem
    remontar a página;
  · `replace: true` **não empilha** entrada no histórico — então 20 toques num chip não enterram o
    "voltar". ⚠️ **É isso que LIST-19 pede** ("recarregar a página devolve o mesmo estado"), não
    navegação por histórico.
  · `->withQueryString()` no `paginate(50)` **já** faz os links do paginator carregarem todos os
    params — **de graça, sem código novo**. É a resposta direta a "como não briga com a paginação de
    50".

**Como não briga com as sub-abas (critério 13):**
  · `sub` é **um dos 12 params** e vai no mesmo `router.get`. Trocar de aba de status **preserva**
    `sub`; trocar `sub` **zera `motivo`** (é o que `trocarSubAba` já faz hoje: `motivo: null`) —
    porque os chips de triagem não existem no universo dos rascunhos.
  · ⚠️ **Decida e escreva na SUMMARY** o que acontece com os 7 filtros novos ao entrar em
    `sub=rascunhos`. Recomendado: **preservá-los na URL e ignorá-los no servidor** — assim voltar para
    "Publicados" restaura o recorte, em vez de o usuário perder o filtro por ter dado uma olhada nos
    rascunhos. O servidor já ignora `motivo` quando `sub=rascunhos`; estender a mesma regra.
  · `page` é **zerado** quando qualquer filtro muda. ⚠️ Sem isso, filtrar na página 7 pode cair num
    vazio que **parece** "não achei nada" e é só "essa página não existe mais". Hoje `navegar()`
    **não** zera `page` — ⚠️ **isto é um bug latente que esta fase conserta**, e vai na SUMMARY como
    melhoria nomeada.

**`sel` (a publicação selecionada):**
  · Vai na URL como `sel=MLB…`, validado no servidor por forma (`/^MLB\d+$/`, plano 180-04).
  · ⚠️ **Nesta fase `sel` só pinta a linha** (`bg-pub-row-sel`) e rola até ela. **O painel de
    inspeção de 460px é a Fase 181**, e é ela que vai ler o MESMO param para abrir. Escreva isso em
    comentário — é o contrato entre as duas fases.
  · ⚠️ Mudar `sel` **não** é round-trip: é `router.get` com `only: []`? **Não.** Seria uma ida ao
    servidor por cada seta do teclado. ➡️ **Decisão:** `sel` e `foco` vivem em `useState` **durante**
    a navegação por teclado, e a URL é atualizada **só** por `window.history.replaceState` quando a
    seleção estabiliza — ou, mais simples e sem API nova, **só** quando o usuário clica numa linha
    (`router.get` com `preserveState` + `replace`, que é o que a tela já faz para tudo).
    ⚠️ **Escolha a segunda** (um mecanismo só, o que já existe) e registre na SUMMARY que navegar com
    as setas **não** escreve na URL — só clicar. Recarregar depois de clicar devolve a seleção, que é
    o que o critério 12 pede. **Não introduza um segundo mecanismo de navegação.**

⚠️ **Nenhum pacote novo, nenhuma API nova.** Se o executor concluir que precisa de um, **PARE e
devolva a pergunta ao usuário**.

## FID-01 — comportamento de teclado (da classe `Component` do protótipo, medido 13/10/2026)

⚠️ **PRESCRITIVA, mas o PROTÓTIPO GANHA**; divergência na SUMMARY em `arquivo:linha`.
⚠️ Confira pela SEMÂNTICA (a função `componentDidMount`, a `move(dir)` e a `onSearchKey`).

| gatilho | condição | efeito medido |
|---|---|---|
| `/` | **e NÃO está digitando** (`e.target.tagName !== 'INPUT'`) | `preventDefault()` + foca a busca |
| `Escape` | há menu aberto | fecha **só** o menu, e **retorna** (não cai nos próximos) |
| `Escape` | está digitando | `e.target.blur()` e **retorna** |
| `Escape` | há publicação selecionada | limpa a seleção e **retorna** |
| `Escape` | nada disso | **nada** |
| `ArrowDown` / `j` | **e NÃO está digitando** | `preventDefault()` + `move(+1)` |
| `ArrowUp` / `k` | **e NÃO está digitando** | `preventDefault()` + `move(-1)` |
| `Enter` | **e NÃO está digitando** **e** há foco | seleciona o item com foco |
| `ArrowDown` **dentro** da busca | há resultados | `preventDefault()` + `blur()` + põe **foco** no 1º |
| `Enter` **dentro** da busca | há resultados | `preventDefault()` + `blur()` + **seleciona** o 1º |

⚠️ **A ordem de precedência do `Escape` é a ordem literal do protótipo e é o que o critério 11 mede:**
*"Esc fecha menu → sai da busca → fecha o painel"*. Trocar a ordem muda o que o usuário sente.

⚠️ **`move(dir)`** no protótipo:
```
const ids = this._ids || []; if (!ids.length) return;
const cur = this.state.selId || this.state.focusId;
let i = ids.indexOf(cur);
i = i < 0 ? 0 : Math.max(0, Math.min(ids.length - 1, i + dir));
// se havia selId, move selId E focusId; senão move só focusId
```
⚠️ Dois detalhes que o gate tem de provar: **`i < 0` vai para o índice 0** (não para `-1`, não dá
erro), e **os limites são travados** (não circula: no fim, `↓` não volta ao começo).
⚠️ A lista de `ids` é a **ordem visual** (grupos abertos, na ordem renderizada) — **não** a ordem do
`anuncios.data` quando a visão é por grupo. Monte-a no mesmo lugar que monta as linhas.
⚠️ `_ids` do protótipo é mutado durante o render. **Em React com hooks isso é um `useRef`
atualizado no render, ou a lista derivada por `useMemo` das mesmas props** — o que for, o listener
**lê a versão atual**, nunca uma capturada num closure velho. É o bug clássico de `useEffect` com
`[]`.
</fid_01_medido>
