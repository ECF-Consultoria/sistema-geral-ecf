## ⚠️ O CAMINHO REAL, MEDIDO EM 13/10/2026 — e por que LIST-20 está escrito errado

**LIST-20 diz:** `ml_acervo_itens.rascunho_id` → `pub_rascunhos.produto_id` → `pub_produtos`.
**Está errado, e isso foi medido no código:**

`ml_acervo_itens.rascunho_id` aponta para **`ml_anuncio_rascunhos`** (o assistente ANTIGO), não para
`pub_rascunhos`. A prova está em dois lugares:
  · `database/migrations/2026_08_11_090000_create_ml_acervo_itens_table.php:55-61` — o comentário diz
    literalmente "criaria dependência de ordem de drop entre **ml_anuncio_rascunhos** e esta tabela";
  · `app/Services/Mlb/Acervo/MlAcervoService.php::mapaRascunhos()` (~`:522`) monta o mapa
    `ml_item_id → rascunho_id` a partir de `MlAnuncioRascunho::where('company_id', …)`, lendo
    `ml_item_id`, `ml_item_id_classico` e `ml_item_id_premium`.

E `MlbAnuncioController::historico()` (~`:306`) **já faz o 4-join certo**, com estes nomes:

```
pub_publicacao_itens
  -> join pub_publicacoes   ON pub_publicacoes.id        = pub_publicacao_itens.publicacao_id
  -> join pub_rascunhos     ON pub_rascunhos.id          = pub_publicacoes.rascunho_id
  -> join pub_produtos      ON pub_produtos.id           = pub_rascunhos.produto_id
  WHERE pub_publicacao_itens.status = PubPublicacaoItem::CREATED
    AND ( pub_produtos.company_id = ? OR pub_produtos.mlb_empresa_id = ? )
```

**A ponte com o acervo é `pub_publicacao_itens.ml_item_id`.**

## ⚠️ CUSTO: nenhuma migration, nenhum índice novo — medido no schema

**Conclusão: as cinco arestas já são indexadas. NÃO é preciso migration nem índice novo.** É por
isso que este plano pode existir — esta milestone declarou nenhuma migration.

⚠️ **Mas a DIREÇÃO importa.** `ml_acervo_itens` tinha **1.080.206 linhas e 1.776 MB** na última
medição. Nenhuma consulta deste serviço pode começar pelo acervo nem forçar o acervo a ser o lado
dirigente de um join. As duas formas obrigatórias:

- **`metodologiaPorMlItemId(Company, array $mlItemIds)`** — recebe no máximo **50**
  `ml_item_id` (a página do acervo) e faz `whereIn('pub_publicacao_itens.ml_item_id', $mlItemIds)`.
  O `whereIn` de 50 valores sobre `pubpi_mlb_ix` é busca por índice; o acervo **não entra na
  consulta**. Devolve mapa `ml_item_id => [...]`.
- **`mlItemIdsPorProduto(Company, string $termo)`** — começa em `pub_produtos` (algumas dezenas a
  poucas centenas de linhas por empresa, por `pubprod_company_ix`), filtra `nome LIKE`/`sku LIKE`, e
  desce pelas FKs até `pub_publicacao_itens.ml_item_id`. Devolve uma lista de `ml_item_id`
  (pequena). Quem a consome é o plano 180-03, que a injeta como `orWhereIn('ml_item_id', $ids)`
  DENTRO do grupo da busca — o acervo continua sendo varrido **uma** vez, pelo `company_id` que já
  varria.

## `ator` — o shape gravado

`pub_publicacoes.ator` é json, gravado por `PublicacaoService::atorParaGravar()`:
`['equipe' => string, 'id' => int, 'nome' => string, 'conta' => [...]]`.
Os literais de autor desconhecido **já existem** e são fonte única — reusar, nunca reescrever:
`PainelVisaoGeralService::QUEM_EQUIPE_SEM_NOME` = `'Equipe'`,
`QUEM_CLIENTE` = `'Cliente'`, `QUEM_ORIGEM_ANTIGA` = `'Origem antiga'`,
`QUEM_SEM_AUTOR` = `'Autor não registrado'`.

## `pub_produtos` — colunas que este serviço lê

`id, company_id, mlb_empresa_id, sku, nome, origem, produto_base_id, quantidade_kit, fase,
estoque_calculado` (as quatro últimas de `2026_10_08_120000_add_fases_to_pub_produtos.php`).
⚠️ `pub_produtos.fase` é o NÚMERO da fase do Publicador (1 = unidade, 2 = combo). **Não confundir
com `estrutura_ofertas.fase`, que é `string(10)` e guarda o TIPO da oferta** — o comentário da
migration avisa que o MariaDB resolve `fase` ambíguo para a tabela errada sem reclamar. **Qualifique
`pub_produtos.fase` SEMPRE.**
`PubProduto::skuExibido()` existe e é a convenção do módulo para o SKU de tela — usar, não a coluna crua.
