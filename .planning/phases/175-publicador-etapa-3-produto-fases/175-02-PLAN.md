<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| rascunho do base → rascunho do kit | cópia de dado que o operador já conferiu; nenhuma entrada do navegador cruza aqui (quem valida é o 175-05) |
| serviço → disco local | escrita de arquivo derivada de caminho montado a partir de id interno + sha |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-175-04 | Tampering / perda de dado | `ImagemAssetService::remover()` apagando o arquivo do base por `caminho` compartilhado | mitigate | o clone copia BYTES para `publicador/{novoRascunhoId}/{sha}.ext`; o unique `(rascunho_id, sha256)` de `pub_imagens` garante estruturalmente que dois rascunhos nunca compartilhem caminho; teste `test_remover_foto_do_kit_nao_apaga_o_arquivo_do_base` prova |
| T-175-05 | Elevation of Privilege | kit nascendo em conta diferente da do base | mitigate | `mlb_empresa_id`/`company_id` são copiados do base dentro do serviço, nunca recebidos em `$dados` |
| T-175-06 | Denial of Service | clone com HTTP ao ML dentro da transação (cota de foto, timeout) | mitigate | `receber()`/`enviarAoMl()` proibidos no clone; teste com `Http::fake()` exige zero chamadas |
| T-175-07 | Tampering | corrida com o editor do base durante o clone | mitigate | `RascunhoRepository::travar()` é o primeiro passo dentro da transação, leitura depois (WR-B02) |
| T-175-08 | Repudiation | transação que cai deixando arquivos órfãos no disco | accept | arquivos escritos são removidos em `rescue` após falha; um órfão residual é inócuo (caminho por sha, nunca referenciado) |
</threat_model>
