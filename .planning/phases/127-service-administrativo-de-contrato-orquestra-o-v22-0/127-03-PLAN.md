<objective>
Criar a checagem que decide se uma empresa está pronta para gerar contrato — **antes** de qualquer
chamada HTTP, de qualquer PDF, de qualquer envelope (Success Criteria 1 do ROADMAP, REDE-05).

Purpose: o orçamento é de 15 chamadas por envelope contra uma janela medida de 20/min. Gastar essa
janela para descobrir no meio do caminho que falta o e-mail do cliente é o desperdício que esta fase
existe para eliminar. E o resultado da checagem é o que a **Fase 131** vai exibir na tela do
Administrativo, onde os campos são preenchidos — não volta como cobrança para o Comercial (D8 do
REQUIREMENTS-v22).

Output: um service dedicado, sem I/O, com contrato de retorno estável para a Fase 131 consumir.

⚠️ **`PendenciasComerciaisService::calcular()` NÃO serve e não deve ser estendido** (Q5 da pesquisa,
lido do código): ele retorna array vazio para qualquer empresa que não seja `is_origem_hubspot`
(`if (!$c->is_origem_hubspot) { return []; }`), ou seja, empresa cadastrada à mão passaria pela
checagem sem nenhuma pendência mesmo faltando e-mail ou CNPJ. E das 7 pendências que ele calcula,
**nenhuma** olha `email_cliente` nem `cnpj` — `sem_contato` cobre 1 dos 3 bloqueantes. Reusá-lo
abriria uma brecha onde o bloqueio simplesmente não roda para metade das empresas.
</objective>

  <action>
    Namespace `App\Services\Contratos`. Sem construtor com dependência externa, sem I/O, sem cache —
    é regra de negócio pura, chamável de qualquer contexto (o service da Fase 127 e a tela da
    Fase 131).

    API pública:
    - `public function faltantes(Company $company): array` — devolve lista de itens
      `['campo' => string, 'rotulo' => string, 'motivo' => 'ausente'|'formato', 'servico_id' => ?int]`.
      Lista vazia = pronta.
    - `public function estaPronta(Company $company): bool` — `$this->faltantes($company) === []`.

    Regras (nesta ordem, todas SEM gate por `is_origem_hubspot` — o dado que falta é o mesmo
    problema em qualquer origem):
    1. `email_cliente`: `blank()` → `ausente`; senão `filter_var(..., FILTER_VALIDATE_EMAIL)`
       falso → `formato`. Rótulo: "E-mail do cliente".
    2. `cnpj`: `blank()` → `ausente`; senão `preg_replace('/\D/', '', $cnpj)` com comprimento
       diferente de 14 → `formato`. **Presença e formato, não dígito verificador** — é literalmente
       o que o REDE-05 pede ("presença e formato"), e o projeto não tem helper de validação de CNPJ
       hoje. Registrar essa escolha em comentário para quem vier depois não achar que foi
       esquecimento. Rótulo: "CNPJ".
    3. `nome_contato`: `blank()` → `ausente`. Rótulo: "Nome de quem assina pela empresa".
    4. `contratosServico` filtrado por `ativo = true` vazio → item `campo = 'contratos_servico'`,
       rótulo "Serviço contratado".
    5. Para cada `ContratoServico` ativo: `data_contratacao` vazia → `ausente` com o `servico_id`
       preenchido; se preenchida mas não parseável como data → `formato`. Rótulo: "Data de início do
       contrato — {nome do serviço}". `data_vencimento` vazia **não reprova** (contrato por prazo
       indeterminado é caso legítimo) — comentar essa distinção.

    ⚠️ **Não incluir** `endereco`, `dia_vencimento` nem `data_primeira_parcela`: os três não existem
    no banco e saem como `A DEFINIR` no documento **por decisão do usuário** (checkpoint do 126-06).
    Deixar isso escrito no docblock da classe, senão alguém "conserta" e trava toda geração de
    contrato.

    Docblock de classe em pt-BR explicando: por que não reusa `PendenciasComerciaisService`
    (gate `is_origem_hubspot` + não checa e-mail nem CNPJ), e que o retorno é consumido pela tela do
    Administrativo na Fase 131 — o formato é contrato público, mudar quebra a tela.
