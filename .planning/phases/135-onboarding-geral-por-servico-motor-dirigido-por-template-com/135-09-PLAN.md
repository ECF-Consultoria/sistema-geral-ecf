<objective>
Construir o backend do painel operacional: o payload que responde "o que está travando, há quantos
dias e de quem é a bola", e as duas ações que o operador precisa — confirmar responsável e concluir
um passo manual.

Purpose: SC-11 é uma rejeição explícita do `feitos/total` do Polos. O painel não pode responder
"73%" — precisa responder "o passo *Grant com a Consultoria* está parado há 6 dias e a bola é do
sistema". Isso só é calculável porque o Plano 02 criou `disponivel_em` e o Plano 04 o carimba uma
vez só: um passo que ficou bloqueado 9 dias e abriu ontem está parado há **1** dia, não 10.

A permission é decisão de discrição desta fase: o `135-RESEARCH.md` deixou em aberto (Open Question
2) se o painel é `role:admin` puro. O UI-SPEC recomenda permission dedicada, porque coordenação de
onboarding envolve consultor/estrategista, não só admin. Adotado: `core.onboarding`, com admin
passando por short-circuit — o CRUD de template continua `role:admin` (D-04).

Output: permission nova, controller com payload agregado e ações, rotas. A tela React chega no
Plano 12.
</objective>

**Permission nova:** `Permissions::CORE_ONBOARDING = 'core.onboarding'`, no grupo
`'Core (ECF Consultoria)'` do `catalog()`, com label `'Onboarding'` e description
`'Painel operacional de onboarding por serviço'`. `User::hasPermission()` já dá short-circuit para
admin (`app/Http/Middleware/EnsurePermission.php`) — não é preciso tratar admin à parte.

**Rotas (fora do grupo `role:admin`, com gate próprio):**
- `GET /onboarding` → `index` (`onboarding.painel.index`), `middleware('permission:core.onboarding')`
- `GET /onboarding/{onboarding}` → `show` (`onboarding.painel.show`)
- `POST /onboarding/{onboarding}/responsavel` → `confirmarResponsavel` (`onboarding.responsavel.confirmar`)
- `POST /onboarding/passos/{passo}/concluir` → `concluirPasso` (`onboarding.passos.concluir`)

**Ordem obrigatória:** estas rotas vêm **depois** de `/onboarding/templates` (Plano 08), senão
`templates` é capturado como `{onboarding}`. Comentário em pt-BR no arquivo registrando isso.

**Vocabulário de situação agregada por onboarding (UI-SPEC, Tela 1) — 6 valores, nesta precedência:**
1. `rascunho` — `onboardings.status = rascunho` (rótulo "Rascunho — aguardando responsável")
2. `vencido` — ao menos 1 passo aberto-e-parado com `dias_parado > sla_dias`
3. `aguardando_cliente` / `aguardando_interno` / `aguardando_sistema` — ao menos 1 passo
   aberto-e-parado dentro do SLA; o sufixo vem do `dono` do passo que mais trava
4. `coletando` — só há passos em `aguardando_coleta`/`indeterminado` pendentes
5. `pronto_para_concluir` — todos os passos **não-administrativos** concluídos, faltando só passo
   administrativo (D-15: o passo de chave `confirmacao_pagamento`)
6. `concluido` — `onboardings.status = concluido`

**Shape de cada item da lista (agrupada por empresa — D-01):**
```
empresa: { id, nome }
onboardings: [{
  id, servico: {id, nome}, status, situacao, situacao_label,
  responsavel: { id, name } | null,
  passo_que_trava: { chave, titulo, dono, setor, dias_parado, sla_dias, vencido } | null,
  contadores: { abertos, bloqueados, aguardando_coleta, indeterminados, concluidos, nao_aplicaveis },
  template_versao: N
}]
```

**Regras de cálculo (não negociáveis):**
- `dias_parado` = dias inteiros entre `disponivel_em` e agora. Passo com `disponivel_em` nulo
  (bloqueado, ou onboarding em rascunho) **não tem** `dias_parado` — o campo vem `null`, nunca `0`
  (UI-SPEC: passo bloqueado não é pendência ainda)
- `passo_que_trava` = entre os passos com status `aberto`, o de maior `dias_parado`. Empate →
  menor `ordem`. Nenhum passo aberto → `null`
- Passo em `aguardando_coleta` **não** entra em `passo_que_trava` (não é pendência humana) e o
  payload dele **não pode** trazer `valor['ativos']`/`valor['inativos']` — só o `coleta_iniciada_em`
  e um flag `coleta_demorando` (`coleta_iniciada_em` há mais de 30 min). Isto é a D-11 na camada de
  apresentação: enquanto está coletando, não existe número
- **Nenhum campo de porcentagem** no payload da listagem (SC-11)

**Escopo de leitura:** admin vê tudo; usuário com `core.onboarding` sem ser admin vê apenas
onboardings das empresas da própria carteira (`company_users`), no mesmo espírito do recorte já
usado em `SugadorController`/`DashboardController::userDashboard()`.

**Ações:**
- `confirmarResponsavel`: valida `responsavel_id` como `exists:users,id`; delega a
  `OnboardingEngineService::confirmarResponsavel()`; `back()->with('success', ...)`
- `concluirPasso`: delega a `OnboardingEngineService::concluirManualmente()`; a
  `\DomainException` de passo automático (D-19) vira `response()->json(['message' => ...], 422)`
  ou `back()->withErrors(...)` — mensagem em pt-BR explicando que o passo é verificado
  automaticamente pelo sistema

**Molde de controller de listagem agregada:** `app/Http/Controllers/ServicoController.php`
(CRUD simples com `Inertia::render` + `back()->with('success')`) e a estrutura de payload de
`NpsTemplateController::index`. **Não** usar `PolosController` como molde de código (D-02) — só a
FORMA de `situacaoDe()` (`Polos/Painel.jsx:107-126`) inspira a função pura de situação, com
vocabulário próprio.
