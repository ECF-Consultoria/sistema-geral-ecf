<objective>
Construir o catálogo fechado de resolvers (D-09) e os dois resolvers que não tocam rede: o do
passo 3 (`adman_account_id` preenchido) e o do passo 5 (`ml_tokens.status = active`).

Purpose: esta é a peça que faz "admin monta o template pela UI" (D-04) conviver com "passos
automáticos" (D-03) sem que o admin possa apontar o template para lugar nenhum. O projeto já
resolveu exatamente este problema duas vezes — `SugadoresAdsProviderFactory` e
`MetricsProviderFactory` — e o molde é Contract + implementações + Factory injetada por DI.
A diferença: aqui não é "escolher 1 provider entre N candidatos", é "cada `auto_fonte` aponta
para EXATAMENTE 1 resolver por chave fixa", então o shape é um **registry por chave**.

O `OnboardingResolverResultado` com três estados é o que impede a fase inteira de repetir o bug
do Shopee (conta nova fica vazia até o backfill, e "vazio" foi lido como "zero"). Um resolver que
devolva `bool` está errado por construção.

Output: interface, value object, registry, 2 resolvers locais e as suítes que provam que o
catálogo é fechado de verdade.
</objective>

**Shape-alvo (decidido):**

`app/Contracts/OnboardingResolver.php`
- `chave(): string` — bate 1:1 com `template_passos.auto_fonte` e com uma constante de `TemplatePasso::AUTO_FONTES`
- `label(): string` — rótulo legível pt-BR para o `Select` da Tela 2 (nunca o nome da classe PHP)
- `ajuda(): string` — texto curto pt-BR explicando **o quê** verifica e **quando** roda (síncrono/assíncrono); o UI-SPEC exige essa linha de ajuda abaixo do campo
- `assincrono(): bool` — se o resolver pode devolver `nao_coletado` por depender de job/rede
- `resolver(Onboarding $onboarding, OnboardingPasso $passo): OnboardingResolverResultado`

`app/Services/Onboarding/OnboardingResolverResultado.php` — value object `readonly`, com named
constructors estáticos (não um enum solto):
- `CONCLUIDO`, `NAO_COLETADO`, `INDETERMINADO` como constantes de estado
- `OnboardingResolverResultado::concluido(array $valor = [])`
- `OnboardingResolverResultado::naoColetado(?string $motivo = null, array $valor = [])`
- `OnboardingResolverResultado::indeterminado(string $motivo)` — 429/timeout/rede
- Propriedades públicas readonly: `estado`, `valor` (array, vai para `onboarding_passos.valor`), `motivo`
- Métodos `ehConcluido()`, `ehIndeterminado()`, `ehNaoColetado()`
- **Proibido** expor um construtor que aceite booleano ou um `fromBool()`

`app/Services/Onboarding/OnboardingResolverFactory.php`
- Construtor recebe os resolvers concretos por DI (mesma forma de `SugadoresAdsProviderFactory`) e
  monta `array<string, OnboardingResolver>` indexado por `chave()`
- `for(string $autoFonte): OnboardingResolver` — lança `\RuntimeException` com mensagem em pt-BR
  citando a chave desconhecida quando não há resolver registrado (catálogo fechado, D-09)
- `existe(string $autoFonte): bool`
- `catalogo(): array` — lista `['chave' => ..., 'label' => ..., 'ajuda' => ..., 'assincrono' => ...]`
  para alimentar o `Select` da Tela 2 (Plano 07/09)

**Achados que mudam a implementação (não redescobrir):**
- `Company::getAdmanAccountIdAttribute()` (`app/Models/Company.php:611-620`) lê **primeiro** do
  pivot `company_marketplaces` (`marketplace='meli'`, coluna `adman_id`) e só cai para a coluna
  flat em fallback, desde a Phase 57. Ler por `DB::table('companies')->value(...)` produz
  falso-negativo em empresa migrada. **Usar sempre o accessor.**
- `MlToken` (`app/Models/MlToken.php`): coluna `status`, valores observados `active` / `revoked`.
  "Token ativo" = `$company->mlToken?->status === 'active'` — é exatamente o filtro que
  `SyncMlAcervo.php:148,159` e `SyncMlData` usam. O refresh automático já acontece em
  `MercadoLivreService::ensureValidToken()`; o resolver **só lê a coluna**, não faz refresh.
- Passo 5 tem `dono = cliente` e `auto_fonte = ml_token_ativo` ao mesmo tempo (D-19) — isso é
  correto, não uma inconsistência a "corrigir".

**Convenções:** logging com tag `[Onboarding]`; comentários em pt-BR; injeção por propriedades
promovidas no construtor.
