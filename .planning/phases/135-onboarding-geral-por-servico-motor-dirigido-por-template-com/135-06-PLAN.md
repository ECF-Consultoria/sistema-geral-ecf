<objective>
Implementar os dois resolvers que tocam rede — o grant com a Adman (passo 4) e as métricas da
conta (passo 7) — e o Job que é o único lugar de onde eles podem rodar.

Purpose: o passo 4 é onde a fase mais facilmente erraria. `companies.adman_account_id` preenchido
prova **cadastro**, não **acesso funcionando** — a D-18 exige que o grant seja provado pela
resposta da Adman para aquele `cust_id`. E a classificação certa já existe em produção, em dois
comandos (`DiagnoseCustId`, `MarkCustIdStatus`): sucesso HTTP = grant ativo mesmo sem movimento no
dia; `400/404/500` = sem grant; **`429`/timeout = indeterminado**. Herdar essa classificação, não
reinventá-la — e jamais deixar um rate limit virar "sem grant".

O `Job` existe porque `fetchPerformance()` tem `timeout(120)` e retenta com backoff: rodar isso
numa request derruba o painel com 504, e o `CLAUDE.md` do projeto já proíbe.

Output: 2 resolvers, o Job, e as suítes que provam a classificação de 3 estados com `Http::fake()`.
</objective>

**Sonda de grant Adman — padrão validado em produção** (`app/Console/Commands/DiagnoseCustId.php:288-315`,
espelhado em `app/Console/Commands/MarkCustIdStatus.php:324-352`):
- Chamada: `AdmanService::fetchPerformance($custId, $ontem, $ontem, 3, $marketplace)` — range de
  **1 dia** para minimizar o payload de `items[]`
- Sucesso HTTP (sem exceção) = **grant ativo**, independente de `summarizedData` vir zerado — a API
  responde 200 mesmo quando a conta não vendeu nada no dia
- Exceção com `400`, `404` ou `500` na mensagem = Adman não reconhece o `cust_id` → **sem grant**
- Exceção com `429` ou qualquer outro código = **indeterminado**; não concluir nem um nem outro
- `usleep(7_000_000)` **sempre**, inclusive em erro — `AdmanService::ADMAN_RATE_LIMIT_RPM = 10`

**O que NÃO usar como sonda (já testado e descartado):**
- `AdmanService::fetchAccountMetrics()` / `/accounts/{custId}/metrics` — dá 404 para a maioria das
  contas ("todos os polos testados", comentário em `AdmanService.php:539-544`)
- `listAccounts()` — sem uso em produção filtrando por `custId`
- `companies.cust_id_status` — populada por comando que **não está agendado**
  (`MarkCustIdStatus.php:44`); para empresa recém-onboardada fica em `desconhecido` para sempre

**`cust_id` da empresa:** ler por `$company->adman_account_id` (accessor — pivot
`company_marketplaces` primeiro). Nulo → o resolver devolve `naoColetado` sem gastar chamada,
porque o passo 4 depende do passo 3 no template.

**Métricas da conta (passo 7)** — `MercadoLivreService::fetchUserInfo(Company $company): array`
(`app/Services/MercadoLivreService.php:514-529`):
- **Lança `\RuntimeException`** quando não há token válido (não devolve `null`) — capturar e tratar
  como `naoColetado`
- `ensureValidToken()` já faz refresh automático; o resolver não reimplementa isso
- `[ASSUMED — não verificado no código deste projeto]` o parsing de `seller_reputation` para
  "reputação verde · medalha · Full" **não existe em lugar nenhum do repositório**. Não há
  consumidor de `power_seller_status`/`level_id`. Portanto: parsing **defensivo**, campo ausente
  vira `null` marcado, nunca exceção; o passo conclui com o que conseguiu ler
- Fonte complementar: `CompanyGrant` (`app/Models/CompanyGrant.php`, `scopeActive()`, campos
  `medalha_fecha_in`/`medalha_fecha_out`/`programa`/`iniciativa`/`parceiro`) — dado do programa de
  parceiros do ML que a ECF recebe, entra **dentro** do passo 7, nunca como passo próprio (D-18)

**Molde do Job (ler inteiro):** `app/Jobs/SyncAdmanCompanyJob.php`
- `implements ShouldQueue`, traits `Dispatchable, InteractsWithQueue, Queueable, SerializesModels`
- `public int $tries = 3; public int $timeout = 120;` + `backoff(): array { return [60,300,900]; }`
- `failed(\Throwable $e)` com `Log::error("[Job] ...")`

**Shape-alvo do Job:**
`ResolveOnboardingPassoJob(OnboardingPasso $passo)` → resolve `auto_fonte` pelo
`OnboardingResolverFactory`, executa, e passa o resultado para
`OnboardingEngineService::aplicarResultado()`. Guard de entrada: passo já `concluido` ou
`nao_aplicavel` → retorna sem fazer nada. `ShouldBeUnique` por `passo->id` com `uniqueFor()` de
1800s, para não empilhar sondas do mesmo passo.

**Ambiente de teste:** `QUEUE_CONNECTION=sync` (`phpunit.xml:31`) — job despachado em teste roda
**inline**. Todo teste destes resolvers precisa de `Http::fake()` ou de mock do service, senão bate
na API real e trava a suíte.
