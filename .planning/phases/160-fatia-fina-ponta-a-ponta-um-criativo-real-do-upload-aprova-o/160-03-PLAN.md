<interfaces>
De `app/Services/Mlb/Publicacao/MlImagemService.php` (já injetado no controller como `$this->imagem`):
- `enviar(Company $company, string $conteudo, string $nome = 'imagem.jpg'): ?array`
  → `['id' => picture_id, 'url' => secure_url|null]`, ou `null` em falha
- lança `RuntimeException` quando a empresa não tem token ML válido

Forma de `pictures` que o publicador já produz (`AnunciarML.jsx::montarPayload`, linha ~1729):
`pictures: imagemUrl ? [{ source: imagemUrl }] : []`
e o `ItemBuilderBase` repassa `pictures` ao ML verbatim (`'pictures' => $d['pictures'] ?? []`).
</interfaces>

## ⚠️ A armadilha deste plano: o autosave reconstrói `pictures` e apagaria a aprovação

`AnunciarML.jsx::montarPayload()` monta `pictures` **a partir do state `imagemUrl`** a cada
autosave/`salvar()`. Se a aprovação gravasse `payload.pictures` só no servidor, a próxima gravação
do wizard mandaria `pictures: []` e apagaria a imagem aprovada em silêncio — o pior tipo de bug,
porque só aparece depois, na publicação, como "anúncio sem foto".

Duas medidas, as duas obrigatórias:
1. O servidor grava `pictures` na **mesma forma** que o wizard produz (`[{source: <url do ML>}]`),
   nunca uma forma nova.
2. O endpoint devolve a `url` e o painel chama `onImagemAprovada(url)`, que faz `setImagemUrl(url)`
   no wizard — assim o próximo `montarPayload()` reconstrói exatamente o mesmo array em vez de
   zerá-lo. (O `picture_id` fica guardado no criativo, para auditoria e para a Fase 161, que vai
   precisar dele nas variações.)
