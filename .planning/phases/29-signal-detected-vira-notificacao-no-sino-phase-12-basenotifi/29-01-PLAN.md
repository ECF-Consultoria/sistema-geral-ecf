// Replicar em PHP em AlertaEcfNotification — static function privada formatPayload.
// pt-BR: vírgula decimal, separador milhar com ponto, R$ sem casas decimais.
// Helpers locais privados:
private static function fmtBRL(float|int|string|null $n): string
{
    $num = is_numeric($n) ? (float) $n : null;
    if ($num === null) return '—';
    return 'R$ ' . number_format($num, 0, ',', '.');     // R$ 11.135
}

private static function fmtPct(float|int|string|null $n): string
{
    $num = is_numeric($n) ? abs((float) $n) : null;
    if ($num === null) return '—';
    return number_format($num, 1, ',', '.') . '%';       // 76,5%
}

private static function fmtInt(float|int|string|null $n): string
{
    $num = is_numeric($n) ? (int) round((float) $n) : null;
    if ($num === null) return '—';
    return number_format($num, 0, ',', '.');             // 12.345
}

## Decisões importantes registradas

**D-A: 4 waves — Backend core (W1) → Integração do Job (W2) → Testes (W3) → Checkpoint humano (W4)**
- *Por quê:* Lean. W1 entrega 2 building blocks isolados e independentes (case enum + subclass Notification — paralelos). W2 conecta tudo no Job real. W3 testa o fluxo completo com fakes. W4 valida com curl real em prod + sino no browser. Sequencial entre waves; paralelo dentro do W1 (2 tasks sem dependência mútua entre si).

**D-B: `AlertaEcfNotification` é subclasse concreta (não anônima inline)**
- *Por quê:* CONTEXT D-02. Coerência com pattern Phase 11/12 (`MetaAtribuidaNotification`, `MetaAtingidaNotification`, `ManualNotification`, `EmpresaCadastradaNotification`). Subclasse nomeada facilita: (a) `Notification::assertSentTo($user, AlertaEcfNotification::class)` em testes; (b) leitura/debug do código; (c) introspecção via `notification_type` na coluna `type` da tabela `notifications`. A versão anônima do stub Phase 26 era aceitável pra MVP mas vira dívida técnica quando a categoria fica recorrente.

**D-C: `TYPE_LABELS` duplicado em constante privada da Notification (espelho do AlertasController)**
- *Por quê:* CONTEXT D-03. Não criar service `LabelService` ou trait compartilhada — overengineer pra fase enxuta. Adicionar prefixo 'crítica' nos 2 primeiros labels é justificado (severity ALWAYS critical no contexto de sino — ressaltar). Documentar duplicação em comentário no topo da constante com ref ao AlertasController.

**D-D: `formatPayload` replicado em PHP — sem importar/parsar o JSX**
- *Por quê:* CONTEXT D-04. Lógica simples (switch + formatadores). PHP precisa fazer offline (sem JS runtime no Job). Aceitar duplicação consciente. Se algum dia o JSX mudar muito, atualizar aqui também — mas é raro (event_types da API ECF Drive são estáveis).

**D-E: Helpers `fmtBRL`/`fmtPct`/`fmtInt` no PRÓPRIO `AlertaEcfNotification` (static private)**
- *Por quê:* Lean — 5-7 linhas cada. Criar trait/helper utility é overengineer. PHP `number_format` faz o trabalho de pt-BR. Aceitar repetição (já existe em outros lugares do app — `lib/utils.js` no front, helpers locais em controllers).

**D-F: Idempotência via `data->meta->signal_id` (NÃO `data->signal_id`)**
- *Por quê:* CONTEXT D-06 sugere `data->signal_id`, mas o payload canônico do `BaseNotification::toArray()` aninha tudo em `meta`. Logo o caminho real é `data->meta->signal_id`. Cast `(string)` obrigatório (API envia int) — armazenamos como string para consistência com `event_id` da Phase 26.

**D-G: Cast `(string) $custId` antes do lookup Company**
- *Por quê:* Pitfall 2 CONTEXT. API envia `custId` como string em alguns casos (`"1354156948"`) e int em outros (raros). MySQL geralmente coage, mas SQLite (testes) NÃO coage strict. Cast garante comportamento determinístico em ambos.

**D-H: Filtro destinatários via `whereIn('role', ['admin','consultor','mentor'])` — não `where role = admin OR role = consultor OR role = mentor`**
- *Por quê:* Idiomático Laravel + 1 índice no banco cobre. Sem cláusula OR explícita (mais legível, mesmo plano de execução).

**D-I: Marca delivery `processed` em TODOS os return paths**
- *Por quê:* CONTEXT D-rendimento. Severity não-critical, custId null, fora da carteira, idempotência já criada — TODOS são "processados com sucesso" (não são falhas). Marcar `processed` evita que pareçam pendentes em `/dev/desenvolvimento` (Phase futura) ou no `webhook_deliveries.status`. Falha real (throw no try/catch) marca `failed` + rethrow.

**D-J: `Notification::send($users, ...)` — NÃO `sendNow`**
- *Por quê:* `sendNow` é síncrono (bloqueante). Job já está em worker — não há razão para forçar síncrono. `::send` default usa o pipeline canônico do Laravel (canal `database` → `DatabaseChannel::send` → grava linha imediatamente). Como `BaseNotification::via` retorna apenas `['database']`, NÃO há disparos mail/broadcast acidentais.

## Riscos residuais (documentados — não bloqueiam o plan)

**R-01: Payload do `signal.detected` real vir com schema ligeiramente diferente do API-GUIDE §7**
- *Mitigação:* Acessos defensivos (`$payload['signal_id'] ?? null`, `$payload['custId'] ?? null`). Se campo crítico ausente → log + processed + return SEM enviar. Job NÃO falha (não rethrow) — admin investiga via `webhook_deliveries.payload` depois.

**R-02: `data->meta->signal_id` não funcionar em SQLite dos testes (suporte JSON1)**
- *Mitigação:* PHP build atual (8.2+) inclui SQLite 3.38+ com JSON1. Caso falhe em algum CI antigo, fallback é `whereJsonContains('data', ['meta' => ['signal_id' => ...]])` (mais lento mas universal). Plan default tenta `data->meta->signal_id` primeiro.

**R-03: Empresa da carteira ter `adman_account_id` e `ml_store_id` ambos null (sem identificador externo)**
- *Mitigação:* Query `where(fn($q) => $q->where('adman_account_id', ...)->orWhere('ml_store_id', ...))` NÃO casa com `null` no DB. Empresa fica fora da carteira pra essa lógica — log 'fora da carteira' + processed + return. Aceitável — admin precisa popular pelo menos 1 dos 2 IDs em Company pra receber alerta.

**R-04: `custId` no payload chegar como int em prod e string em sandbox**
- *Mitigação:* Cast `(string) $custId` em ambos os usos (idempotência + lookup company). Sem cast, comportamento variaria silenciosamente.

**R-05: Worker parado em prod quando webhook chegar**
- *Mitigação:* Phase 26 já marca delivery `received` no receiver. `failed_jobs` registra após `tries=3`. Admin vê delivery preso em `received` por tempo prolongado — supervisor `ecf-worker:*` em prod tem auto-restart. Não é responsabilidade da Phase 29.

**R-06: Mesmo signal_id chegar 2× via webhook real (parceiro com retry agressivo)**
- *Mitigação:* Phase 26 garante UNIQUE em `event_id` no receiver — segundo recebimento é rejeitado ANTES de criar `WebhookDelivery`. Phase 29 idempotência por `signal_id` cobre o cenário oposto: 2 webhooks com `event_id` diferente mas mesmo `signal_id` (ECF Drive re-emitiu signal). Cobertura dupla.

**R-07: `Notification::send` falhar parcialmente (1 dos 3 users recebe, 2 não)**
- *Mitigação:* Laravel `Notification::send` em loop interno. Se uma falha (ex DB transient), exception propaga → catch do Job marca delivery `failed` + rethrow. Próxima tentativa do worker re-dispatcha. Idempotência por `signal_id` previne notificar 2× quem JÁ recebeu. Aceitar overhead de 1-2 inserts duplicados em race extrema (idempotência é por `signal_id`, não por `signal_id` + `user_id`). Refinar para `signal_id + user_id` fica para fase futura se virar problema.

**R-08: Coleção de destinatários vazia em produção (todos admin/consultor/mentor inativos)**
- *Mitigação:* `Notification::send(EmptyCollection, ...)` é no-op silencioso no Laravel. Log warning pt-BR `'[Signal] Sem destinatários ativos — notificação não criada'` + delivery processed + return SEM erro. Cenário improvável em prod, mas defensiva.

**R-09: Comando `php artisan tinker` em prod durante smoke W4 não conseguir abrir DB (lock)**
- *Mitigação:* Improvável — DB MySQL em prod aceita conexões concorrentes. Workaround: usar `php artisan tinker --pretend` ou rodar query via `php artisan db:show` se necessário.

**R-10: Sino do header não atualizar imediatamente após Job rodar (polling delay)**
- *Mitigação:* `HandleInertiaRequests` re-conta em cada request — visite qualquer página (ou navegue) e contador atualiza. Phase 10 tem polling explícito por intervalo de tempo (5-30s típico) — em ~1min admin vê. NÃO é WebSocket real-time (fora de escopo Milestone v9.0).
