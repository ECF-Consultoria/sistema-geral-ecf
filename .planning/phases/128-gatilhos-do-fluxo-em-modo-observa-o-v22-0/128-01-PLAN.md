  <action>
Criar a migration adicionando `exige_contrato` em `servicos`, seguindo o molde da migration
`2026_08_12_100001_add_clicksign_template_id_to_servicos_table.php` (mesma tabela, Fase 127).

`up()`:
1. `Schema::table('servicos', fn (Blueprint $table) => $table->boolean('exige_contrato')->default(true)->after('clicksign_template_id'));`
2. Depois do `addColumn`, no mesmo `up()`: `DB::table('servicos')->where('nome', 'Polos')->update(['exige_contrato' => false]);`

`down()`: `Schema::table('servicos', fn ($table) => $table->dropColumn('exige_contrato'));`

Regras que a migration precisa respeitar (per D-03 e per pesquisa Q3):
- `default(true)` é obrigatório — SQLite dos testes recusa `ADD COLUMN ... NOT NULL` sem
  default, e o default cobre os 8 serviços existentes **sem enumerá-los**.
- **NÃO** usar `whereIn` com a lista dos 8 nomes. `Gestão de ADS Shopee` não tem seed
  versionado e a grafia real no banco de produção não foi medida (MariaDB local fora do ar,
  confiança MÉDIA registrada na pesquisa). Se a grafia divergisse, o serviço ficaria isento
  por engano — o oposto do que a D-03 pede. Com `default(true)` + UPDATE só de `Polos`, uma
  divergência de grafia é inofensiva: o serviço continua exigindo contrato.
- **NÃO** usar `enum`, **não** criar índice, **não** criar FK — nenhuma armadilha de MariaDB
  se aplica aqui (mesma conclusão registrada na migration-molde da Fase 127).
- Idempotência do UPDATE: usar `where('nome', 'Polos')` por nome exato — é o único nome
  garantido por migration versionada (`2026_05_27_100001_seed_servicos_catalog.php`, linha 37).
  Se a linha não existir (ambiente novo antes do seed), o UPDATE afeta 0 linhas e a migration
  passa mesmo assim; o seed roda antes na ordem cronológica de migrations, então em ambiente
  limpo o Polos já existe.
- Docblock em pt-BR explicando POR QUE default é `true` e por que só Polos é isentado por nome.
