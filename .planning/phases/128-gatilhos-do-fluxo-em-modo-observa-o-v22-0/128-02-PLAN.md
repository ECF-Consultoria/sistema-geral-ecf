  <action>
Aplicar a **Opção B** da pesquisa (método irmão + helpers extraídos). Este é um refactor de
organização, **sem nenhuma mudança de comportamento observável**.

Extrair as 4 checagens universais para métodos privados, cada um recebendo o que já usa hoje e
devolvendo `?string` (o slug) ou `null`:
- `private function pendenciaSemServico(Collection $contratosAtivos): ?string`
- `private function pendenciaSemValor(Collection $contratosAtivos): ?string`
- `private function pendenciaSemSetor(Collection $contratosAtivos): ?string`
- `private function pendenciaSemContato(Company $c): ?string`

O corpo de cada helper é **cópia literal** do bloco correspondente de `calcular()` — mesma
condição, mesmo slug, sem "melhorias" de nenhum tipo. Reescrever a condição, mesmo que
equivalente, é exatamente o risco que esta estratégia existe para evitar.

Reescrever `calcular()` para chamar os helpers **na mesma ordem em que as checagens aparecem
hoje** (sem_servico → sem_valor → servico_nao_reconhecido → sem_setor → sem_contato →
valor_revisar → possivel_duplicidade). A ordem importa: os testes asseram o array de slugs e
alguns comparam com `assertSame`. O early-return `if (!$c->is_origem_hubspot) { return []; }`
**permanece no topo de `calcular()`, intocado**. As 3 checagens hubspot-only continuam inline
dentro de `calcular()`, sem extração — não há motivo para movê-las e cada linha movida é risco.

Docblock pt-BR em cada helper explicando que o método é compartilhado entre `calcular()`
(listagem, origem HubSpot) e `calcularUniversais()` (gate administrativo, qualquer origem),
citando a D-01 da Fase 128.
