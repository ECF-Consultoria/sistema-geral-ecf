## Phase Goal

**As a** usuário membro de setor / consultor / mentor / dono de carteira / admin, **I want to** receber notificações automáticas quando metas são atribuídas ou atingidas, **so that** eu não preciso conferir manualmente dashboards e não dependo do admin emitir mensagens.

<objective>
Backend de disparos automáticos sem nenhuma UI nova. 3 migrations triviais (1 coluna cada) + 2 classes Notification concretas + 3 hooks `static::created` nos models de meta + 3 patches nos jobs de cálculo de result + 1 suíte de teste com 6 testes.

**Decisões inline:**
- D-01: Idempotência via coluna `notificado_em` no result table (não via query na `notifications`). Mais barato em runtime, menos JSON contains, mais idiomático Laravel.
- D-02: Hooks via `static::booted()` dentro do model (não Observer separado) — mais leve, menos arquivos.
- D-03: 2 classes Notification (atribuída/atingida) — não 6. Polimorfismo via parâmetros do constructor. Categoria do enum diferencia.
- D-04: `autor_user_id = null` para todos os disparos automáticos (são "do sistema", não de um user). Phase 12 (criação manual) vai preencher o autor real.
- D-05: `url = null` no MVP. Phase 10 já navega para `/notificacoes` via "Ver todas" — não precisa de deeplink por notificação ainda.
- D-06: Para `Goal` (empresa), o público é `consultor ∪ mentor` deduplicado por `id`. Admins NÃO entram em AUTO-02 (criação) — só entram em AUTO-05 (atingimento). Confere com REQUIREMENTS literal.
- D-07: Para AUTO-04/05/06, "admins" = `User::where('role', 'admin')->get()`.
- D-08: Para AUTO-04, "líder(es) do setor" = `$setor->lideres` (relação já existente em `Setor.php:84`).
- D-09: Activity log das notifications NÃO é tratado aqui (POLL-05 fica na Phase 12 para envio manual). Disparos automáticos não logam.

**Output:**
- 3 migrations (1 coluna cada)
- 2 Notification classes
- 3 model edits (booted hook)
- 3 job edits (post-updateOrCreate)
- 1 suíte de 6 testes
</objective>

    });
}
