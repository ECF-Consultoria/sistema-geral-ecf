## Decisões importantes registradas

**D-A: 4 waves — Backend core(W1) → Integração+Comando(W2) → Testes(W3) → Checkpoint humano(W4)**
- *Por quê:* Lean. W1 entrega os 3 building blocks isolados (service PDF + view PDF + Mailable+view email) — cada um testável manualmente via tinker. W2 conecta tudo no Job real + cria a porta manual de disparo. W3 testa o fluxo completo com fakes. W4 valida com email real em prod. Sequencial dentro da phase (sem paralelo — escopo pequeno, dependências fortes entre tasks).

**D-B: `RelatorioMensalPdfService` é instância (não estática) — DI no Job**
- *Por quê:* Mesma estratégia das Phases 22/27. DI via construtor facilita mock futuro (se algum dia quisermos testar o Job isolado do PDF). Mailable NÃO injeta o service — não precisa, o PDF já está gravado em Storage quando o Mailable é construído (separação clara de responsabilidades).

**D-C: Mailable NÃO gera o PDF — anexa do Storage**
- *Por quê:* Pattern do `RelatorioFechamentoMail` (Browsershot dentro do Mailable) é um anti-pattern leve — acopla geração com envio. Phase 28 separa: Job gera + grava + envia. Mailable só lê do Storage. Vantagens: (a) PDF persiste mesmo se Mail falhar; (b) admin que perdeu email pode pedir cópia direto do storage; (c) testa Mailable sem precisar mockar geração de PDF.

**D-D: Helper `mesLabelPt($periodo)` duplicado em 3 lugares (Mailable + Comando + Blade)**
- *Por quê:* Lean. São 5 linhas (array MESES_PT + substr + concat). Criar service novo `LabelService` só pra isso seria overengineer pra essa fase. Aceitar duplicação consciente.

**D-E: `tries=3` + `backoff=[60, 300, 900]` — adicionar `backoff` ao stub existente**
- *Por quê:* CONTEXT D-09. Job atual (stub Phase 26) tem `tries=3` mas SEM `public array $backoff`. Phase 28 adiciona — alinhado com pattern dos 5 outros Jobs de `EcfWebhook/` (verificar consistência manualmente se necessário; se outros tiverem backoff diferente, manter coerência com a maioria).

**D-F: `timeout=120s` no Job (era 60s no stub)**
- *Por quê:* PDF gen via Dompdf ~1-2s + Mail SMTP pode levar até 30s pra 2-3 admins. Buffer pra rede degradada. 60s era suficiente pro stub (só log) — agora não é.

**D-G: Destinatários via `User::where('role','admin')->where('active', true)` — consulta no `handle()`, NÃO no construtor**
- *Por quê:* CONTEXT D-01. Construtor é executado no DISPATCH (pode ser horas antes do worker pegar). Handle é no momento do processamento. Consultar no handle garante que admin recém-adicionado entre dispatch e handle ainda recebe.

**D-H: Comando cria `WebhookDelivery` sintético com `event_id = 'manual-{periodo}-{uuid}'`**
- *Por quê:* Phase 26 criou UNIQUE constraint em `event_id`. Re-emissão manual do mesmo período colidiria com `event_id = '202605'`. Prefixo `'manual-'` + UUID garante unicidade + sinaliza no audit log que foi disparo manual (admin pode filtrar `event_id LIKE 'manual-%'` se quiser auditar).

**D-I: Comando NÃO usa `dispatchSync()` — usa `::dispatch()` normal**
- *Por quê:* Em prod o supervisor já roda worker. dispatchSync bloquearia o terminal por ~30s (PDF + Mail). Dispatch normal = comando retorna em ms, worker processa em paralelo. Em dev/CI, executor roda `php artisan queue:work --once` depois (anotado no `<done>` da task).

**D-J: PDF gravado ANTES do envio de email**
- *Por quê:* Idempotência + audit trail. Se Mail falhar, PDF está no storage e o próximo retry do Job só precisa re-enviar email (não re-gerar PDF). Storage::put é fast (<10ms), Mail::send é lento (até 30s).

**D-K: Idempotência via sobrescrita silenciosa do PDF**
- *Por quê:* CONTEXT D-05. Webhook é UNIQUE por `event_id` (constraint DB). Re-execução manual gera novo `event_id` mas mesmo período → novo PDF sobrescreve antigo. Trade-off claro: admin que rodar comando 2× recebe 2 emails. Aceitar.

**D-L: View `mensal-pdf.blade.php` usa CSS inline + `<style>` no head — SEM Tailwind**
- *Por quê:* Pitfall 1 CONTEXT. Dompdf ignora classes utility. Cores hex hardcoded (#ffe600 amarelo ECF, #050507 fundo, #0f1116 cards). Tabelas com `border-collapse` + `padding` + `font-family: 'DejaVu Sans'` (default Dompdf que suporta UTF-8).

**D-M: Logo via `public_path('images/logo.png')` + base64 inline — fallback texto**
- *Por quê:* Pitfall 2 CONTEXT. Codebase tem `public/images/` (NÃO `public/img/` — corrigido após verificação). Embed base64 evita timeout/fetch. Fallback texto cobre o caso do arquivo não existir (Defensiva contra ambiente novo).

**D-N: Defensiva `@if(!empty($subnode))` em CADA seção do PDF**
- *Por quê:* CONTEXT D-03. Se algum subnó da API vier vazio (oportunidadesPads sem dados), seção é pulada SEM quebrar o PDF inteiro. Robustez vs perfeição visual.

**D-O: `Mail::fake()` + `Storage::fake('local')` nos testes — NUNCA mailer real em CI**
- *Por quê:* CONTEXT D-10 + lean. Mail::fake intercepta envios sem chamar SMTP. Storage::fake redireciona Storage::put pra memória. Testes determinísticos < 5s totais.

**D-P: Testes de `User` factory cobrem `role` + `active`**
- *Por quê:* Cobertura inclui `['role' => 'admin', 'active' => true]` (recebe), `['role' => 'admin', 'active' => false]` (NÃO recebe), `['role' => 'consultor', 'active' => true]` (NÃO recebe). UserFactory deve aceitar esses overrides desde Phase 7+.

**D-Q: Comando faz print informativo (não silencioso)**
- *Por quê:* Praticidade. Admin que roda em produção via SSH precisa de feedback imediato (delivery_id + dica de queue worker). NÃO precisa progress bar — Job é assíncrono.

**D-R: Mailer real em prod NÃO configurado nesta phase — pré-requisito do W4**
- *Por quê:* CONTEXT D-02. Configurar SMTP/SES é trabalho de infra (não de phase). W4 valida que prod TEM mailer configurado antes de smoke. Se não tiver, admin configura `.env` + `php artisan config:cache` e retoma o smoke.

## Riscos residuais (documentados — não bloqueiam o plan)

**R-01: Schema do `/relatorios/mensal/{periodo}` vir diferente do API-GUIDE §8**
- *Mitigação:* Defensiva `@if(!empty)` por seção no Blade + try/catch global no Job. Se a API mudar drasticamente, Job marca delivery failed + log estruturado pra debug. PDF mínimo (só cabeçalho + erro pt-BR) NÃO é entregue — preferimos falhar claramente que entregar PDF enganoso.

**R-02: Dompdf ter performance pior que esperado (>5s) em PDFs maiores**
- *Mitigação:* Limites já aplicados — top 10 ranking, top 5 cluster, amostra de 5 signals. Mantém PDF <1MB. timeout=120s do Job cobre worst case. Em prod monitorar via `storage/logs/laravel.log`.

**R-03: Mailer em prod estar `log` no momento do smoke**
- *Mitigação:* W4 step 2 verifica explicitamente. Se admin esquecer, Mail vai pro laravel.log e admin não recebe email — `php artisan tail -f storage/logs/laravel.log` mostra o "Mail logged" e admin sabe o que ajustar.

**R-04: SMTP do provedor recusar PDF >5MB**
- *Mitigação:* Limites de tabela (top 10/20/5) mantém tamanho típico em ~200KB-1MB. Pitfall 7 CONTEXT documenta. Se ultrapassar, Phase futura pode comprimir imagens / cortar tabelas.

**R-05: API ECF Drive offline no momento do webhook real (cron dia 5)**
- *Mitigação:* `tries=3` + `backoff=[60, 300, 900]` cobre janela total de ~22 min. Cache 24h do wrapper Phase 22 cobre re-dispatches subsequentes. Se ainda falhar, delivery fica em `failed_jobs` + admin vê em `/dev/desenvolvimento` (Phase futura).

**R-06: Falha no comando manual (DB lock, race condition no UUID)**
- *Mitigação:* `event_id` com UUID v4 (`Str::uuid()`) tem probabilidade ~zero de colisão. Caso `WebhookDelivery::create` falhe por outra razão, comando catch genérico imprime erro pt-BR e exit 1.

**R-07: 2+ webhooks reais chegarem do mesmo período (ECF Drive bug)**
- *Mitigação:* UNIQUE em `event_id` no DB rejeita o duplicado no receiver Phase 26 ANTES de chegar ao Job. Phase 28 não precisa proteger contra isso — Phase 26 já cobre.

**R-08: PDF não renderizar acentuação corretamente (â, ã, ç)**
- *Mitigação:* `<meta charset="UTF-8">` no head + Dompdf default font 'DejaVu Sans' (suporta UTF-8 completo) + verificação manual no smoke W4.

**R-09: Admin recém-adicionado com `active=null` em vez de `active=false`**
- *Mitigação:* Query `where('active', true)` exclui `null` automaticamente (operador `=` no MySQL). Schema atual exige `active` boolean (Phase 7+ migration). Risco baixo, pattern já validado em outras phases.

**R-10: Comando dispatchado mas worker parado em prod**
- *Mitigação:* Praticidade — admin vê delivery em `webhook_deliveries` com status='received' por tempo prolongado, sabe que worker travou. Supervisor `ecf-worker:*` em prod já tem auto-restart. Caso extremo, admin reinicia worker via SSH.

          return $meses[$mes - 1] . '/' . $ano;
