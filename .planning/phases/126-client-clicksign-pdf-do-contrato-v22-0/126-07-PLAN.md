<a_forma_medida>
**A §9.6 do empírico tem precedência sobre a `126-RESEARCH-MODELOS.md` onde os dois divergirem.**
A pesquisa marcou o formato de `template.data` como "não testado, e a doc oficial se contradiz";
a §9.6 mediu contra o sandbox e resolveu: **é hash, não string serializada**.

Sondado com UUID de modelo inexistente — a API valida a FORMA do payload antes de resolver a chave,
então dá para medir sem ter modelo cadastrado:

| Payload enviado | Resposta medida |
|---|---|
| `attributes.template = {key, data:{...}}` sem `filename` | `400 [filename deve ser informado(a)]` — **e só isso** |
| `template.data` como STRING `json_encode()` | `400` + `/data/attributes/template/data: "data deve ser um hash"` |
| `template` sem a chave `data` | `400` + `/data/attributes/template/data: "data deve ser informado(a)"` |

Quatro fatos que saem daí e que este plano materializa:
1. O campo é `attributes.template` — **não** `template_id` (a tentativa com `template_id` da §9.4
   falhou por nome de campo errado, não por rota inexistente).
2. `template.data` é HASH. `json_encode()` é recusado.
3. `template.data` é OBRIGATÓRIO.
4. `filename` continua obrigatório; `content_base64` **some** da lista de obrigatórios quando
   `template` está presente. Não é "um ou outro" — `filename` é o nome do documento gerado.

Da §9.4 (medido pela mensagem 422 da própria API): o modelo é um `.docx` com variáveis em **chaves
duplas**, e nome de variável **não aceita `@`, `#` nem `!`**.

Da §2 da `126-RESEARCH-MODELOS.md` (documentado, exemplo `curl` literal): o `content_base64` do
modelo é **Data URI completo** com o MIME de `.docx`
(`data:application/vnd.openxmlformats-officedocument.wordprocessingml.document;base64,...`) — mesmo
padrão que já custou uma sessão no gate #4 com o PDF. E `name` precisa terminar em `.docx`.
</a_forma_medida>
