O `<tensao_de_dados>` do CONTEXT deixou para o planejamento decidir como a fase lida com os campos
que não existem no banco. **Decisão registrada: Opção C do RESEARCH — parâmetro opcional +
placeholder visível.**

| Campo | De onde vem nesta fase |
|---|---|
| Razão social | `companies.name` (é o único campo existente; se vier vazio, cai no placeholder) |
| CNPJ | `companies.cnpj` |
| Contato | `companies.nome_contato`, `companies.email_cliente`, `companies.telefone` |
| Serviços e valores | `servicos_snapshot` (D-04) — nunca `contratos_servico` ao vivo |
| Vigência | datas dentro do próprio `servicos_snapshot` |
| **Dia de vencimento** | parâmetro opcional `$complementos['dia_vencimento']`; ausente → placeholder |
| **Forma de pagamento** | parâmetro opcional `$complementos['forma_pagamento']`; ausente → placeholder |
| **Endereço** | parâmetro opcional `$complementos['endereco']`; ausente → placeholder |

**Placeholder adotado: a string `A DEFINIR`** (maiúsculas, sem colchetes) — visível na leitura,
impossível de confundir com dado. A regra do CONTEXT é explícita: o que não vale é campo em branco
silencioso num documento jurídico.

Além do placeholder, `montarDados()` devolve `campos_pendentes` — a lista dos campos que caíram no
placeholder. A Fase 127 decide o que fazer com isso (bloquear envio, avisar o operador); esta fase
apenas informa. A Fase 131 (ADM-01) passa a preencher `$complementos` e a lista esvazia sozinha.

⚠️ Duas confirmações humanas ficam para o checkpoint do plano 126-06: se `companies.name` é de fato
razão social (assunção A1 do RESEARCH, confiança BAIXA) e se `A DEFINIR` é aceitável num documento
que vai ao cliente.
