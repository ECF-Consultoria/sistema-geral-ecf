<objective>
Blindar o congelamento mensal (`ConsolidarMesDesempenho`) — é o snapshot que PAGA o bônus. Hoje ele grava o resultado de UMA passada `compute()` sem retry/reconciliação; se essa passada coincidir com rate-limit 429 concorrente no exato instante do cron (31/07 14h BRT), ele SOBRESCREVE o snapshot bom com um degradado. Adicionar um gate de qualidade da amostra de margem: se a cobertura de margem real do user estiver abaixo do limiar, RECUSAR persistir (preservar o snapshot anterior) e emitir alerta — em vez de gravar um número envenenado.

Purpose: Garantir que o valor que efetivamente paga o bônus de junho não seja capturado por uma amostra única e não-reconciliada sujeita a falha transitória de terceiros. O Plan 110-01 já tornou a margem determinística (local) para a maioria; este plano é a rede de segurança para o resíduo (empresas cujo local é insuficiente e o ao-vivo falha no instante do freeze).

Output: `compute()` expõe `margem_amostra` (n_real, n_elegivel, cobertura); `ConsolidarMesDesempenho` gateia a persistência por essa cobertura, recusa+alerta quando degradada (com sub-caso explícito quando NÃO há snapshot anterior para preservar), e mantém o comportamento existente (idempotência, sem_carteira, ranking_pos) intacto.
</objective>

<design_decision>
## Recusa degradada + ausência de snapshot anterior (DESEMP-08) — decisão travada

Ao RECUSAR persistir uma amostra degradada, há dois sub-casos:

1. **Existe snapshot mensal anterior (o comum no fechamento oficial):** recusar = preservar o valor bom já congelado. É a rede de segurança pretendida — não há dano.

2. **NÃO existe snapshot mensal para o user/mês (`DesempenhoScoreSnapshot::mensal()` inexistente para user+mes_referencia):** recusar deixa o user SEM ROW nenhuma naquele mês. Isso NÃO é neutro — quebra silenciosamente `DesempenhoScoreService::promoverPor2MesesConsecutivos()` (~1289-1316), que lê o snapshot mensal de M-1 do banco para decidir a promoção por 2 meses consecutivos (DESEMP-08). Um mês faltante zera a cadeia sem rastro.

**Decisão implementada:** manter a RECUSA de criar a row degradada (não envenenar o pagamento com um número ruim é prioridade), MAS tornar o sub-caso 2 barulhento e acionável — emitir `Log::error` explícito nomeando (a) user_id/user_name + mes_referencia, (b) que NÃO há snapshot anterior para preservar (a recusa deixa o mês vazio), (c) o impacto em DESEMP-08 (cadeia de promoção de 2 meses consecutivos usa o mensal de M-1), (d) a instrução operacional: re-rodar `php artisan desempenho:consolidar-mes` manualmente quando o rate-limit da Adman passar (foi exatamente assim que o snapshot de 22/07 foi gerado — a reconciliação é operacional, não silenciosa). Não criar row placeholder/degradada só para "ter algo" — isso reintroduziria o número envenenado que o gate existe para evitar.
</design_decision>
