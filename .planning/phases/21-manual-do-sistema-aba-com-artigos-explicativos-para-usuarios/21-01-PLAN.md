<objective>
Criar a aba **"Manual do Sistema"** no painel ECF Admin — uma nova área documental hardcoded em JSX, acessível a TODOS os usuários autenticados, com arquitetura extensível para artigos futuros. O **primeiro e único artigo desta fase** é o **"Cronograma de horários"**: uma tabela ordenada que explica em linguagem coloquial pt-BR o que cada uma das 14 rotinas automáticas do sistema faz e quando roda — destinado a operadores sem conhecimento técnico (consultores, mentores, publicadores, líderes).

Purpose:
- **Acertividade**: o operador entende exatamente o que o sistema está fazendo e em qual horário — sem precisar perguntar ao dev ou abrir `routes/console.php`. Ao olhar para a Dashboard às 10h e ver número desatualizado, sabe instantaneamente que a rotina das 11h ainda não rodou (D-1 da Adman). Reduz suporte interno e dúvidas recorrentes.
- **Praticidade**: 1 clique no rodapé da sidebar → 1 clique no card "Cronograma" → tabela inteira na frente. Zero configuração, zero busca, zero fricção. Hardcode em JSX dispensa CMS/banco/migration; cada novo artigo entra com 2 arquivos novos sem mexer no backend.

Output:
- 1 PLAN.md (este arquivo)
- Backend: `ManualController` (2 actions de leitura pura) + 2 rotas no grupo `['auth', 'verified']` (FORA de role:admin e permission:*)
- Frontend: catálogo central `artigos.js` + lista `Index.jsx` + wrapper `Show.jsx` + artigo `Cronograma.jsx` + item no rodapé da sidebar do `AppLayout.jsx`
- Testes: 4 testes Feature em `tests/Feature/Phase21/`
- Sem migration, sem model, sem activity log, sem permission/policy, sem CMS, sem deps novas
- W4: checkpoint humano blocking para smoke visual em prod cobrindo conteúdo + responsividade + múltiplas roles
</objective>

Se o controller passasse a lista de artigos como prop, o `Component` do artigo (uma referência React) precisaria ser serializável — o que JSX/Inertia não suporta. Solução: `artigos.js` é importado direto pelos componentes `Index.jsx` e `Show.jsx`, sem passar pelo backend. O controller só decide QUAL página renderizar e qual slug passar.
- *Consequência:* `ManualController::index()` não recebe lista de artigos como argumento; `Index.jsx` consulta `listarArtigos()` localmente. Adicionar novo artigo é puramente frontend — controller nunca muda.

**D-02: Slug inválido → backend retorna 200, frontend mostra "Artigo não encontrado"**
- *Por quê:* CONTEXT.md Pitfall 4. Se o controller mantivesse allowlist de slugs e devolvesse 404, qualquer novo artigo no `artigos.js` exigiria mudança no controller também — quebra a promessa "só JSX para novo artigo". Decisão: controller é "burro" (passa qualquer string como slug); o `Show.jsx` faz `buscarArtigo(slug)` e renderiza mensagem amigável quando null. Pro: extensibilidade pura. Contra: rota `/manual/lorem-ipsum` retorna 200 técnico (não 404). Aceitável para área de leitura sem efeitos colaterais.

**D-03: Item da sidebar vai no rodapé do `<nav>`, NÃO dentro do User footer**
- *Por quê:* CONTEXT.md decisão 3 manda "no rodapé da sidebar, acima do botão Sair". Há 2 interpretações: (a) dentro do `User footer` div (linha 201 do AppLayout — junto com avatar + LogOut) ou (b) última posição da `<nav>` (linha 135-198). Análise: o User footer atual tem APENAS controles de identidade do usuário (avatar + nome + role + logout); injetar item navegacional ali quebraria coesão visual e o padrão de `isActive(item.page)` dos demais itens. Solução: inserir como ÚLTIMO item de NAV_ITEMS com `footerSeparatorBefore: true`. O divisor faz o item parecer destacado mas mantém uniformidade técnica.
- *Resultado UX:* visualmente fica "no rodapé da sidebar acima do botão Sair" como pedido — só que o "rodapé" é o fim da nav, não a div do User footer.

**D-04: Reuso de `<Card>` do shadcn, sem novos componentes UI**
- *Por quê:* CONTEXT.md cross-cutting constraint "Reutilizar componentes shadcn existentes (card, table, badge) — não criar novos". `Card` (`@/Components/ui/card`) já existe. Tabela usa HTML puro (`<table>`) com Tailwind — não há `Table` shadcn instalado no projeto (grep confirma ausência). Suficiente para 14 linhas.

**D-05: Lista de palavras proibidas é trava de revisão humana (W4), não automação**
- *Por quê:* CONTEXT.md SC-7 define lista explícita (comando, schedule, cron, job, API, cache, endpoint, fetch, background, queue, worker, nomes de classes, nomes de Artisan commands). Gate automatizado por grep no JSX falha porque palavras como "cache" e "API" podem aparecer legitimamente em outros contextos do mesmo arquivo (não no conteúdo do artigo). Solução: W4 humano lê a tabela completa e confirma que NENHUM termo proibido aparece no conteúdo VISÍVEL ao usuário. O executor deve, ao escrever o JSX, seguir as substituições autoritativas já dadas no `<interfaces>` (que estão pré-revisadas).

**D-06: Sem `<Head>` específico — usar `title` do AppLayout**
- *Por quê:* O padrão do projeto (visível em Dashboard/Admin.jsx e outras páginas) usa `<AppLayout title="X">` que renderiza o título no header da página. Não precisa de `<Head title="X" />` separado salvo para personalizar `<title>` do browser. Decisão: usar apenas o `title` do AppLayout para manter consistência com outras páginas; deferir `<Head>` para fase futura se aparecer demanda de SEO/analytics interno.

**D-07: ManualController NÃO estende `Controller` base**
- *Por quê:* O controller não usa nenhum trait do base (`AuthorizesRequests`, `DispatchesJobs`, `ValidatesRequests`). Conforme Laravel 12, controllers podem ser classes simples. Verificar convenção do projeto via grep — se TODOS os controllers existentes estenderem Controller, ajustar para extends consistência. Caso contrário, classe limpa é preferível.
- *Fallback:* se o executor detectar inconsistência (`grep -l "extends Controller" app/Http/Controllers/*.php` retorna a maioria), adicionar `extends Controller` para alinhar. Não é bloqueador.

## Riscos residuais (documentados — não bloqueiam o plan)

**R-01: Linguagem do artigo vazando jargão técnico após edição posterior**
- *Probabilidade:* baixa nesta fase (texto autoritativo no `<interfaces>` já está revisado). Média em fases futuras quando adicionarem mais artigos.
- *Mitigação:* CONTEXT.md SC-7 mantida como guarda permanente; W4 valida na fase atual; futuros artigos devem repassar a lista antes de commit.

**R-02: Cronograma desatualizado quando schedule mudar no futuro**
- *Probabilidade:* certa (já houve mudanças de horário nas Phases 16 e 20).
- *Mitigação:* CONTEXT.md Pitfall 2 documenta. Decisão: aceitar débito manual nesta fase. Se em 2-3 meses virar manutenção pesada, abrir nova fase para auto-extrair de `routes/console.php` parseando o AST PHP (Phase 22+). O artigo Cronograma traz um aviso curto no rodapé "Última revisão deste artigo: AAAA-MM-DD" para o leitor saber se está atual.

**R-03: Sidebar com 1 item a mais pode estourar layout em telas pequenas / sidebar collapsed**
- *Probabilidade:* baixa (sidebar já tem `overflow-y-auto` na nav, linha 135).
- *Mitigação:* (i) `BookOpen` ícone tem 17px (consistente com outros), (ii) label "Manual do Sistema" tem 18 chars (mesma faixa de "Pub · Dashboard"), (iii) quando collapsed o label some via `(!collapsed || mobile)`. W4 valida visualmente em mobile + sidebar collapsed.

**R-04: Slug aceitar caracteres especiais (`{slug}` sem regex)**
- *Probabilidade:* irrelevante para segurança (controller não executa nada com slug, só passa adiante; `Show.jsx` faz lookup em objeto JS — chave inexistente retorna null).
- *Mitigação:* Aceitável. Se aparecer demanda de bloquear (ex: tracking de slugs inexistentes), adicionar regex `where('slug', '[a-z0-9-]+')` em fase futura.

**R-05: Usuários com tokens públicos `/implementacao/*` veem item da sidebar?**
- *Resposta:* NÃO. Tokens públicos não passam pelo `AppLayout` (são páginas standalone sem sidebar — workspace cliente). CONTEXT.md decisão 4 já exclui tokens públicos explicitamente.
