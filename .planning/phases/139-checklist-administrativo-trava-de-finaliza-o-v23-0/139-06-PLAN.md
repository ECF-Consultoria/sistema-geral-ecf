Acrescentar ao `FinalizarEntradaAdministrativaService`:

`marketplaceDestino(Company $company): ?string` — resolve o módulo de destino (D-12). Regra:
contar `$company->marketplaces()->where('is_primary', true)->count()`. Se for `> 1`, emitir
`Log::warning('[Checklist] is_primary duplicado na pivot company_marketplaces', ['company_id' => ...,
'quantidade' => ...])` e resolver por `->where('is_primary', true)->orderBy('id')->value('marketplace')`
— a linha de **menor `id`** vence. Se for `<= 1`, delegar a `$company->primaryMarketplace()`, que já
tem o fallback para a coluna flat `companies.marketplace` (`NOT NULL`, `default('meli')`).

Comentário pt-BR obrigatório: `is_primary` é **guard de Model, não constraint de banco** — nada
impede duas linhas `true`, e `->value()` sem `orderBy` devolveria a primeira que o motor entregar,
sem ordem garantida. A escolha "menor id" é arbitrária e assumida como tal; o que não é aceitável é
ser **não determinística**. `Company::primaryMarketplace()` **não é alterado** por esta fase: é
método compartilhado por outros módulos, e mudar a ordenação lá teria alcance muito além do
FINALIZAR — o desempate mora aqui, onde a decisão foi tomada.

`finalizar(Company $company, User $por): array` — na ordem:
1. chamar `podeFinalizar($company)`; se `permitido` for `false`, devolver
   `['status' => 'recusado', 'requisito_faltante' => ..., 'marketplace_destino' => null,
   'etapa' => $company->etapa]` **sem escrever nada**;
2. chamar `$this->etapas->transicionar($company, Company::ETAPA_AGUARDANDO_DISTRIBUICAO, $por)`;
3. se o resultado vier com `status !== 'transicionado'`, emitir `Log::warning('[Checklist] transição
   de finalização recusada', [...])` e propagar o `requisito_faltante` **sem inventar mensagem
   nova** — mesma disciplina do chamador de produção existente. O caso mais provável é a empresa
   ainda não estar na etapa 4 (a tabela `TRANSICOES_PERMITIDAS` só permite chegar em 5 vindo de 4);
   quem a leva até a 4 é o `ChecklistEtapaSincronizadorService` (plano 139-07), chamado **pelo
   controller antes** deste método (plano 139-08). Este service **não** chama o sincronizador: ele
   já é dependência do sincronizador, e a injeção recíproca fecharia ciclo no container
   (`CircularDependencyException`). A orquestração é do chamador — aqui só se propaga a recusa;
4. em caso de sucesso, devolver `['status' => 'finalizado', 'requisito_faltante' => null,
   'marketplace_destino' => $this->marketplaceDestino($company), 'etapa' => Company::ETAPA_AGUARDANDO_DISTRIBUICAO]`.

Proibido neste arquivo: qualquer `Company::whereKey(...)->update(['etapa' => ...])`, qualquer
`$company->etapa = ...` seguido de `save()`, e qualquer `DB::transaction()` envolvendo a chamada a
`transicionar()` — o service chamado já é transacional com `lockForUpdate()`, e aninhar transação
que também escreve em `Company` mexe com locks sem necessidade. Comentar isso.
