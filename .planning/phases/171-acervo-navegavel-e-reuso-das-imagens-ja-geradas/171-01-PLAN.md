<objective>
Dar ao acervo (D4) a sua primeira metade — o backend que torna navegável e reutilizável o que o
Creative Engine **já guarda, sem apagar, desde a Fase 160**. Depois deste plano existe uma API que:
(1) lista as imagens já geradas, aprovadas ou não, do produto aberto e, opcionalmente, de toda a
conta; (2) serve o binário de qualquer uma delas, escopado pela conta; (3) copia uma delas para o
rascunho atual como uma foto nova, sem gastar nenhuma chamada ao provedor de IA.

**Confirmado no código, antes de escrever este plano (os dois fatos do briefing do usuário são
verdadeiros, e um terceiro merece registro):**

1. **As imagens já são guardadas para sempre.** `creative:limpar-referencias`
   (`app/Console/Commands/LimparReferenciasCriativos.php`) só varre `referencias`/
   `referencias_apagadas_em` (as fotos de REFERÊNCIA que o operador sobe) — nunca toca
   `imagem_path`/`imagem_mime`/`imagem_bytes` (a imagem GERADA). Nenhum código deste plano precisa
   decidir "quanto tempo guardar" — essa decisão já foi tomada, pelo acúmulo de fato, há duas fases.
2. **O acervo sobrevive à exclusão do rascunho, pelas FKs reais de produção** (confirmado lendo as
   migrations, não só a afirmação do usuário): em `ml_anuncio_criativos`, `company_id`/
   `mlb_empresa_id` são `cascadeOnDelete` (apagar a empresa/conta apaga o criativo — comportamento
   aceito, fora de escopo) e `pub_rascunho_id`/`pub_imagem_id` são `nullOnDelete` (apagar o
   RASCUNHO do Publicador só zera o vínculo — o criativo e o arquivo em disco continuam). A âncora
   que sobrevive é `company_id`/`mlb_empresa_id`, nunca `pub_rascunho_id`.
3. **Divergência a registrar: hoje não existe nenhum botão "excluir anúncio/rascunho" no Publicador
   novo** (`grep` por `destroy`/`excluir` nos controllers do Publicador não encontra nada — só o
   assistente ANTIGO, `MlbAnuncioController`, apaga `ml_anuncio_rascunhos`, uma tabela diferente).
   O cenário "criativo órfão" (`pub_rascunho_id` NULL) que ACERVO-01/ACERVO-05 precisam suportar é
   **defensivo para uma ação que a FK já permite mas nenhuma tela ainda dispara** — não uma
   regressão a corrigir aqui. Este plano trata o órfão como um caso de primeira classe mesmo assim
   (ele pode acontecer por qualquer rota futura que chame `$rascunho->delete()`, e o teste da Task 2
   cria um órfão diretamente por `DB`/`delete()` para provar o comportamento sem depender de uma UI
   que não existe).

**Por que NÃO há migration nesta fase.** O acervo não precisa de nenhuma coluna nova: a âncora de
conta (`company_id`/`mlb_empresa_id`) já existe em `ml_anuncio_criativos` desde a Fase 160, o
"produto de origem" é resolvido ao vivo por `pub_rascunho_id → pub_rascunhos.produto_id` quando
existe (e `null` quando o rascunho foi apagado — o próprio sinal do órfão), e "reaproveitar" é uma
CÓPIA dos bytes para uma `pub_imagem` nova — nunca um vínculo nem uma tabela de auditoria nova. Zero
risco de migration em tabela com dado de produção.

**Por que "reaproveitar" é uma CÓPIA, nunca uma referência compartilhada (pergunta difícil 3 do
briefing).** `ImagemAssetService::receber()` sempre cria (ou reaproveita por dedupe de sha256) uma
`PubImagem` **do rascunho que a recebe** (`$r->imagens()->create(...)`) — não existe, no schema
atual, uma `pub_imagem` compartilhada entre dois rascunhos. Isso responde a pergunta por construção:
se o anúncio ORIGINAL (de onde a imagem foi copiada) for apagado depois, a cópia no rascunho novo é
uma linha independente, intocada — `pub_imagem_id` do criativo ORIGEM nunca é tocado por este plano.

**Por que a validação roda de novo na cópia (pergunta difícil 4).** Este plano reusa literalmente o
mesmo `ImagemAssetService::receber()` que `PublicadorCriativoAprovacaoService::aprovarSlot()` já usa
para aprovar um slot pela primeira vez — `receber()` sempre roda `ValidadorImagem::problemas()`
(inclui V-IMG-03, mínimo 500px) em QUALQUER chamada, não só na primeira. Não há atalho que pule a
validação para uma imagem "já aprovada antes" — e não deveria haver um.

**Por que o escopo é por CONTA (company_id/mlb_empresa_id), nunca por pub_rascunho_id, quando
"toda a conta" está ligado (pergunta difícil 1/2).** O acervo precisa listar imagens de OUTROS
rascunhos (e de rascunhos que não existem mais) da mesma conta — por isso toda query e todo
escopo de autorização deste plano usa as colunas de conta do criativo comparadas às colunas de
conta do `PubProduto` AUTORIZADO (nunca um id solto da requisição), replicando a disciplina D-13 do
`MlbPublicadorCriativoController` (id numérico, 404 nunca 403) com uma âncora diferente da que esse
controller usa. `ProgramasPublicadorService::empresaDoProduto()` já devolve `null` (→ 404) quando um
produto não tem `company_id` NEM `mlb_empresa_id` — por isso este plano não precisa de uma guarda
extra contra "produto sem conta nenhuma": a autorização existente já cobre.
