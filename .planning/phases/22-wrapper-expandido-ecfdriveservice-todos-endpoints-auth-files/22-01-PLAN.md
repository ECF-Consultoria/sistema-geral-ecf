### Helpers privados — refatoração e nova base HTTP

```php
/**
 * Helper HTTP base — TODOS os métodos GET passam por aqui.
 * Centraliza headers, retry, timeout, checagem de status e mensagem de erro pt-BR.
 *
 * @param  string  $path    Caminho relativo (com / inicial) — ex: "/clientes/grants"
 * @param  array   $params  Query params (serializados como query string pelo Http facade)
 * @return array            Resposta JSON decodificada como array associativo
 * @throws \RuntimeException quando HTTP != 2xx após retry, com mensagem pt-BR.
 */
private function get(string $path, array $params = []): array
{
    $response = $this->http()->get($path, $params);

    if (! $response->successful()) {
        throw new \RuntimeException(
            "ECF Drive {$path} falhou: HTTP {$response->status()} - {$response->body()}"
        );
    }

    return $response->json() ?? [];
}

/**
 * Helper de geração de chave de cache determinística.
 *
 * Formato: "ecf.{path-sanitizado}.{md5(query-canonica)}"
 * - path-sanitizado: troca / por . e remove leading dot — ex: "/sellers/123/medalhas" → "sellers.123.medalhas"
 * - query-canonica: ksort + http_build_query (chaves null viram '') — determinístico para mesmo conjunto de params
 *
 * Quando $params está vazio, retorna apenas "ecf.{path-sanitizado}".
 */
private function cacheKey(string $path, array $params = []): string
{
    $sanitizedPath = ltrim(str_replace('/', '.', $path), '.');

    if (empty($params)) {
        return "ecf.{$sanitizedPath}";
    }

    // Normaliza nulls para '' e ordena por chave (determinismo)
    $normalized = array_map(fn ($v) => $v ?? '', $params);
    ksort($normalized);
    $queryHash = md5(http_build_query($normalized));

    return "ecf.{$sanitizedPath}.{$queryHash}";
}
```

public function ranking(string $metrica, int $top = 20, ?string $programa = null, bool $asc = false): array

    if (! in_array($metrica, self::MET_VALIDAS, true)) {
        throw new \InvalidArgumentException(

    $path = '/sellers/ranking';
    return Cache::remember(
        $this->cacheKey($path, $params),
        3600,
        fn () => $this->get($path, $params),

/**
 * Marca um signal como visto.
 *
 * Faz POST /signals/{id}/ack e invalida a chave de cache da inbox padrão
 * ("acked=false" + "limit=50" + "page=1") — o caso mais comum.
 * Outras combinações de filtros expiram naturalmente em 1min.
 *
 * @return array Resposta da API (estrutura definida pelo backend remoto)
 * @throws \RuntimeException em HTTP != 2xx.
 * @see API-GUIDE.md §7 (POST /signals/{id}/ack)
 */
public function ackSignal(int $id): array
{
    $response = $this->http()->post("/signals/{$id}/ack");

    if (! $response->successful()) {
        throw new \RuntimeException(
            "ECF Drive ackSignal({$id}) falhou: HTTP {$response->status()} - {$response->body()}"
        );
    }

    // Invalidação determinística da chave-padrão da inbox (D-04)
    $inboxKey = $this->cacheKey('/signals', ['acked' => false, 'limit' => 50, 'page' => 1]);
    Cache::forget($inboxKey);

    return $response->json() ?? [];
}

## Decisões importantes registradas

**D-01: Helper privado `get()` centralizado — não usar herança nem trait**
- *Por quê:* O CONTEXT.md D-03 trava "único service class, não dividir em sub-classes". Helper privado mantém o encapsulamento e elimina ~50 linhas duplicadas (cada método GET seria 5 linhas de boilerplate de retry+checagem+exception). Refatorar os 4 métodos Phase 20 prova que o helper não muda comportamento observável.

**D-02: `ping()` NÃO usa o helper `get()` — mantém o try/catch local**
- *Por quê:* `get()` lança `RuntimeException` em HTTP != 2xx. `ping()` precisa retornar `false` sem lançar em qualquer caso (401, 500, timeout, DNS). Refatorar `ping()` para usar `get()` exigiria adicionar mais um try/catch externo — mais código, mesma semântica. Mantém o padrão Phase 20 que já é testado (`test_ping_retorna_false_em_4xx_sem_lancar`).

**D-03: Cache key `grantsExpirandoEm` preserva formato Phase 20 (`ecf_drive:expirando:{dias}`)**
- *Por quê:* Pode haver caches ativos em prod (Phase 20 deployada em 2026-06-05). Mudar a chave para o novo formato `ecf.clientes.grants.{hash}` invalidaria caches existentes sem ganho funcional. Decisão lean: helper `cacheKey()` é só para os 18 métodos NOVOS; o legado mantém sua chave histórica.

**D-04: Invalidação de cache de signals limita-se à chave-padrão da inbox**
- *Por quê:* CONTEXT.md Pitfall 4 do briefing menciona 3 opções (Cache::tags, loop Cache::forget('ecf.signals.*'), invalidação seletiva). Escolha: **invalidação seletiva da chave mais consultada** — `ecf.signals.{hash(acked=false,limit=50,page=1)}`. Justificativa: (1) `database` store não suporta tags; (2) iterar todas as chaves de cache é caro; (3) TTL de 1min faz outras combinações expirarem naturalmente. Trade-off documentado: um usuário com filtro custom (ex: `?severity=critical`) pode ver signal já acked por até 1min — aceitável.

**D-05: `array_filter(fn ($v) => $v !== null)` em vez de `array_filter()` simples nos params opcionais**
- *Por quê:* `array_filter()` sem callback remove valores falsy como `0`, `false`, `''` — mas alguns endpoints aceitam esses como filtros válidos (`asc=false` na API ECF Drive é DIFERENTE de "asc não enviado"). Por isso `ranking()` converte `asc` para `'true'`/null e usa `array_filter` com callback explícito. Padrão replicado em `compararSellers`, `carteiraBreakdown`, `carteiraDistribuicaoMedalhas`.

**D-06: Cache TTL para `listClientes` é 5min (não 1h)**
- *Por quê:* Não consta na tabela do CONTEXT.md D-02 (esquecimento do briefing). Inferência: `listClientes` é endpoint paginado idêntico em uso ao `listGrants` (já 5min). Manter consistência — 5min cobre dashboard executivo sem cair em stale data. Documentado aqui para auditoria.

**D-07: Validações defensivas lançam `InvalidArgumentException` (não `RuntimeException`)**
- *Por quê:* Erro de uso do caller (métrica errada em ranking, 21 sellers em compararSellers, dimensoes vazio em segmentacao) é distinto de erro HTTP da API remota. `InvalidArgumentException` sinaliza "fix your code" vs. `RuntimeException` que sinaliza "API remota teve problema". Caller deve tratar diferente.

**D-08: Testes não chamam API real — apenas `Http::fake`**
- *Por quê:* CONTEXT.md D-07 trava decisão. Validação real fica para W4 (smoke humano via tinker). Fixtures dos testes são extraídas do API-GUIDE.md (exemplos reais do guide).

**D-09: Sem `set_time_limit`, sem `ignore_user_abort` no service**
- *Por quê:* Service é chamado por controllers (request HTTP normal) e jobs (queue worker com timeout próprio). Não é responsabilidade do service estender limites globais.

**D-10: W4 (smoke prod) é checkpoint humano blocking**
- *Por quê:* Mesmo padrão das Phases 20 e 21. Smoke valida (a) API key tem permissão nos novos domínios, (b) fixtures dos testes batem com payload real, (c) nenhum método lança em runtime. Sem isso, Phases 23-28 podem encontrar surpresas tarde demais.

## Riscos residuais (documentados — não bloqueiam o plan)

**R-01: API ECF Drive ajusta shape de payload entre guide e prod**

**R-02: Cache `database` driver com muitas chaves**

    public function listSignals(array $filtros = []): array

     *
